# 懂行 · 产品需求整理（截至 2026-09-23）

> 本文汇总已对齐的**最终交付产品设计**，供设计 / 开发对照。变现策略已讨论但明确「先把产品设计好」，下文仅附录备忘。  
> 曾用名「邪修交通」；仓库 `fasstDog/dongxing`。

---

## 1. 一句话定位

输入出发地与目的地（可选日期、可选路径城市），推荐比直达更聪明的高铁 / 动车 / 飞机组合走法；讲清楚怎么去、为什么这样推；换乘时间长则告诉你怎么玩。**只推荐路线，不卖票**；购票跳转 12306 / 航司 / OTA。

心智：**帮你找到直达之外那条更聪明的路。**

---

## 2. 问题与机会

- 直达贵、绿皮慢；高铁换乘、空铁混搭常更划算，但大平台默认推直达或官方联运，邪修组合要用户自己拼。
- 抖音等已有大量「邪修路线」种草（如徐州→拉萨），缺一个把「怎么走 + 为什么 + 中转怎么玩」结构化的工具。
- 竞品分层：12306/航司空铁联运偏正规一票制；智行等中转偏铁路联程；灵犀出行、优途 AI、个人项目偏早期。成熟「以省钱邪修 + 窗口玩」为主产品的小程序仍少。

---

## 3. 目标用户

- 价格敏感，愿意多换乘一次
- 时间稍宽裕，能接受「多几小时换更低价 / 更好坐」
- 被邪修内容种草，但不想自己查拼

不主打：商务极致准点、带老幼零容错、国际联程。

---

## 4. 核心原则

1. 默认给出 **3 个主方案**：最省钱 / 最快 / 最综合；下方提供更多方案。
2. 每条方案固定四块：**怎么去 · 为什么 ·（可选）怎么玩 · 去外链购票**。
3. 换乘不够长，不硬推景点。
4. 价格、时刻标「参考」，以购票平台为准。
5. 不做卖票、订单、支付、抢票。
6. **出计划由程序 / 规则引擎完成**；模型若接入，只做文案润色或口语偏好解析，**不生成车次与票价**。

---

## 5. 功能需求（最终交付）

### 5.1 查询输入

| 字段 | 必填 | 说明 |
|------|------|------|
| 出发地 | 是 | 城市 / 站点 |
| 目的地 | 是 | 城市 / 站点 |
| 出发日期 | 否 | 可「灵活」 |
| 路径城市 | 否 | 可多个、**有序**；用户指定必经途经点 |

- 不填路径城市 → **自动模式**：系统选枢纽并生成组合。
- 填写路径城市 → **指定路径模式**：按 `出发 → 途经1 → … → 途经n → 到达` 分段拼方案，不再自动换枢纽。
- 途经最多 **3** 个；支持添加 / 删除 / 调序。

### 5.2 结果：三主卡 + 更多

**三主卡**

- **最省钱**：参考总价最低（建议加最长总时长上限，避免极端硬座方案）
- **最快**：门到门总时长最短
- **最综合**：价格、时长、换乘次数、「屁股友好」（卧铺占比、单段最长久坐）加权

指定路径模式下，三主卡是**同一路径**下不同交通方式 / 班次组合，而不是换其它城市。

**更多方案**：可按省钱 / 省时 / 少换乘（及可选「屁股友好」）筛选；点进同一套详情。

结果页可提供切换：**按你的路径** ↔ **试试系统自动邪修**（有途经时）。

### 5.3 方案卡片与详情字段

每张卡 / 详情需包含：

1. **怎么去**：分段时间轴（方式、站点、参考时刻、参考价、建议席别、段时长）；换乘节点标注同站 / 同城、缓冲时长、接驳提示。
2. **为什么这样做**：人话说明（比直达省/贵多少、多/少多久、票好不好抢、舒适度、若指定途经则说明「因你指定经某某」）。
3. **换乘怎么玩**：仅当缓冲达到阈值；POI 名称、距车站、建议游玩时长、是否赶得回。
4. **去购票**：按段跳转外链（参数带好站点与日期）；本产品不出票、不收款。

### 5.4 「怎么玩」出现规则

| 条件 | 行为 |
|------|------|
| 同站缓冲 ≥ 约 2 小时 | 偏休息 / 站内或极近 |
| 同城缓冲 ≥ 约 3 小时 | 可推 1～2 个景点 |
| 过夜或 ≥ 约 6 小时 | 可推半日玩（短住入口可预留） |
| 低于阈值 | 只提示休息与接驳，不硬推玩 |

玩法内容：人工维护约 **12 个头部枢纽**（见 [`hubs.md`](./hubs.md)：北京、上海、广州、深圳、成都、重庆、武汉、杭州、郑州、西安、兰州、西宁）；其余中转城可只显示接驳。查询覆盖以合规数据可达站场为目标，不把玩法表规模等同于可查范围。

### 5.5 明确不做（产品边界 · 永久红线）

卖票、支付、账号体系履约、抢票、官方联运一票制履约、国际线、复杂多日行程编辑器、社区 UGC、强推广告。  
主卡默认侧重 **≤1 次中转**的可解释方案；2 次以上中转可进「更多」，不作为主卡默认策略。

---

## 6. 信息架构与主流程

**页面**：首页查询 → 结果列表（三主卡 + 更多）→ 方案详情（含枢纽玩法）→ 关于 / 免责声明。

**正式客户端仅两端**：微信小程序 + **官方 React Native** App（iOS + Android）；共享同一 plans API / TS 契约 / 可抽出逻辑；UI 与运行时分端（RN 不是小程序路径）。静态 HTML 原型仅示意、已冻结。Windows/macOS/Web/tvOS/Proton Native/Alita 等非产品承诺。

**主流程**：

```
输入出发、到达（可选日期、可选有序途经）
  → 生成方案
  → 结果页三主卡
  → 详情（怎么去 / 为什么 / 怎么玩）
  → 分段「去购票」跳转外链
  → 或「更多方案」列表
```

## 7. 后台：如何出计划

**原则：程序算计划；模型可选当讲解员。**

流水线：

1. **取数**：火车 / 航班时刻与参考价（**目标为合规真源**；mock JSON 仅实现/测试夹具与降级）；直达作对照。
2. **定枢纽**  
   - 自动模式：规则候选枢纽（头部枢纽表或密度启发式）  
   - 指定路径：用户途经即枢纽链
3. **组合枚举**：分段查询；校验最小换乘时间；自动模式默认枚举 **1 次中转**进三主卡（指定途经按段数，途经个数 ≤ 3）。
4. **打分**：产出最省钱 / 最快 / 最综合 + 更多列表。
5. **文案**：模板填「为什么」；POI 表填「怎么玩」；模型仅可选润色或解析「便宜就行 / 屁股舒服」等偏好。

**规则引擎要点**：打分与三主卡确定性可测；难点在数据接入、同城换乘保守估时、边界 case 与缓存。定链用头部枢纽表 + 粗阈值；工程上先用 mock 夹具冒烟与样例对答案（含徐州→拉萨），再切入合规接口——**产品设计始终以真源可达为目标，不以 mock 定义产品能力**。

---

## 8. 覆盖范围与实现量级（工程粗估）

最终产品能力：站点/机场查询覆盖以合规数据可达为准（目标地级市全覆盖），玩法与精细换乘内容优先头部枢纽运营维护。

| 工程落地量级（同一产品设计的实现顺序，非缩水范围） | 粗估 |
|------|------|
| 热门 OD + 头部枢纽玩法 + 契约/引擎冒烟 | 约 1～2 人 × 4～8 周 |
| 地级市车站/机场、合规真源、稳定 1 转 | 约 3～5 人 × 4～6 个月 |
| 较稳全国版（缓存/观测/内容运营常态化） | 约 5～8 人 × 6～12 个月 |
| 镇/景区门牌 + 多段接驳 | 更长，内容与数据成本陡增 |

对外可宣传「全国能查」；对内：**站点逐步全国，玩法与精细换乘先头部城市**——这是内容运营策略，不是「先做一个缩水产品再换产品」。

---

## 9. 成功标准（产品）

新用户从打开到看懂一个方案约 **30 秒内**；能说清「为什么不选直达」；愿意点至少一次外链购票或复制行程。

## 10. 样例场景（已用于对齐）

**徐州 → 拉萨**（示例卡片思路，价格为公开参考量级）：

- 方案 A：直达 Z 字头过路车，总时长很长；硬座便宜但「屁股」差，硬卧贵且过路票难抢。
- 方案 B：经西宁拆两段（推荐向）；后半段始发进藏，票与舒适度往往更好；窗口可玩塔尔寺等。
- 方案 C：经西安（高铁 + 火车或飞机）；可玩可飞，缓冲够则推兵马俑等。

展示字段：总价区间、总时长、相对直达、屁股分、换乘能否玩、分段外链。

## 11. 附录：变现（已讨论，当前不优先）

主路径备忘：购票跳转 CPS/CPA（机票/酒店为主，12306 几乎无分成）；换乘窗口本地消费（景点/日游/短住）；保险与附加服务；会员解锁更多方案/提醒；后期 B 端 API/白标。坚持不卖票、不做乱投广告或自营票。**当前：先把产品设计与引擎做对。**
