# Skill：系统架构设计文档生成

> 蒸馏自范本：`docs/UPWARDS+ 系统架构设计_v1.0.md`（Agent-First 医疗研究系统，2214 行，十章）。
> 本 Skill 回答一个问题：**如何把一个系统（需求、想法或现有代码库）写成一份可评审、可落地、可追溯的架构设计文档。**

## 0. 适用场景与输入盘点

适用：

- 从需求文档 / 口头想法 / 现有代码库生成 v1.0 架构设计文档；
- 评审或重构已有架构文档（用 §6 自检清单逐项打分）；
- 在既有架构文档上做 v1.1 迭代（先跑自检清单，再动手改）。

动手前盘点输入，缺什么就在文档里标 `[待确认]`，**禁止编造**：

| 输入 | 要问出的问题 |
| --- | --- |
| 需求与痛点 | 系统解决什么？哪些需求最痛、最不容失败？ |
| 领域与合规 | 有无 PHI / 资金 / 数据出境类硬约束？审计保留期？ |
| 底座 | 是否基于既有框架？能改它的核心吗，还是只能扩展？ |
| 规模与演进 | 数据量级？引擎是否会异构？三阶段各自目标？ |
| 治理 | 团队如何评审、发布、灰度、回滚？ |
| 历史分歧 | 团队争论过什么？——每条争论都是一条决策记录素材 |

## 1. 方法论七律

这七条是范本文档的灵魂，写任何章节前先记住：

1. **原则先行，机制兜底**。先定设计原则（短语命名 + 一句话解释），再为每条原则设计可执行机制；找不到机制支撑的原则删掉，否则就是口号。
2. **红线即分类学**。先建组件分类红线表（谁可用 LLM、谁可持久化、谁可自主决策、谁可写数据），任何新需求进入系统前先归类，归类不了就是设计漏洞。
3. **机制而非意图**。每个设计决策落到「组件 + 参数 + 默认值 + 边界 + 失败路径」；"我们会做好权限控制"不是设计，"写操作必须实现 preview_impact() + 审批令牌 + 审计"才是。
4. **不确定性显式化**。判断状态枚举完整（不止 TRUE/FALSE，还要 UNKNOWN、CONFLICTING、MANUAL_REVIEW…），数据缺失策略必须有安全默认值，且默认值不许是"当无事发生"。
5. **负面清单与正面设计同权**。禁止事项、不实现清单、取消的方案、被否决的替代方案都要写下来——它们防止的是未来的人重蹈覆辙。
6. **自证而非宣称**。量化准则（如"满足 ≥3 条才建新组件"）必须配逐项对照表（✓/✗ + 满足数），证明每条准则真的被执行，而不是形同虚设。
7. **一处定义，处处引用**。术语在术语表定义一次；章节间用 §x.y 交叉引用；需求用编号呼应（"呼应需求 5.7"）；画一张端到端权威时序图，声明"以此图为准"，终结各节措辞不一致。

## 2. 文档骨架：十章模板

| 章 | 使命 | 必含元素 |
| --- | --- | --- |
| 1 架构总览 | 定基调 | ① 设计原则列表（10–16 条，见 §3 步骤二）；② 组件类型红线表（类型 × 是否有 LLM / 是否持久 / 是否自主决策 / 是否允许写数据 / 典型示例）+ 判定准则；③ 总体架构图 |
| 2 技术栈选型 | 锁底座 | 层级 × 技术 × 版本 × 选型理由表；一节"为什么选 X"说明不自研的理由（闭环能力、许可、迁移成本） |
| 3 核心架构 | 系统心脏 | 设计约束（编号列表，与红线表口径一致）；组件形态分类（定义、维度表、适用/不适用场景、建立准则 + 自证表 + 取消的组件）；角色映射表；协作机制（Artifact 类型表、字段清单、治理规则、聚合边界）；端到端协同示例（分阶段）；核心数据结构（字段级 JSON + 状态枚举 + 版本治理）；路由与通讯机制 + 禁止事项清单；失败与降级表；可重放机制（版本要素清单）；反馈闭环；**端到端权威时序图** |
| 4 扩展体系 | 职责边界 | 四/五类扩展边界表（每类一句话本质：怎么做 / 什么情况下允许做 / 确定性规则 / 真正执行 / 按什么步骤做）+ 关键约束；各体系的清单表、元数据 YAML 示例、治理要求（PR / 审核 / 灰度 / 回滚 / 版本联动）；Tool 清单（名称 × 输入 × 输出 × 权限级别 × 幂等性 × 内部调用组件）+ 权限级别枚举；实现规范（代码骨架 + 约束列表）；扩展类型判断矩阵（能力特征 → 优先实现） |
| 5 数据访问层 | 引擎无关 | 设计动机（挑战清单）；双路径（内部走 Repository，外部走协议 Adapter）+ 协议定位一句话；职责分离表（组件 × 职责 × 不负责 × 是否经协议层）；Adapter 原语清单（含受控 SQL 的白名单治理）；Skill 调用流程；引擎适配规则表；引擎引入时机（量化信号：p95 > 5s、分析占比 > 30%…）；快照与血缘链；权限模型（多维权限 + PDP/PEP + capability token 字段）；预留能力声明（只留接口契约与红线，防"绕通道临时实现"） |
| 6 网关与集成 | 对接框架 | 集成模式（复用宿主框架的插件机制 + 优势列表）；后端路由代码骨架；事件流表（事件类型 × 前端渲染 × 说明） |
| 7 安全与权限 | 合规底线 | 分层安全模型（3–5 层，每层 3–6 条）；高风险操作审批链（text 图，预览 → 审批 → 执行 → 审计 → 可撤销窗口）；权限矩阵（角色 × 操作级别）；审计与合规（哈希链 / WORM / 外部锚定）；**上线前置阻断项表**（阻断项 × 判定内容 × 未完成后果）+ 责任归口 |
| 8 开发模式 | 怎么落地 | 总体原则（双轨并重 + 前置依赖关系）；两条轨的范围；每类扩展的开发工作流（判断是否需要 → 编写 → 校验 → 测试 → PR → 审核 → 灰度 → 监控回滚，约 8 步）；环境与发布治理；测试与评估策略（传统测试表 + 领域评估框架表 + 评估集数据来源）；部署架构（dev 编排 + 生产清单 + 配置约束）；迭代模式；**分阶段实施**（每阶段：目标 / 保留 / 前置必做 / 不实现 / 新增 / 关闭，加能力 × 阶段对照表和"先…再…"迁移原则） |
| 9 关键技术决策记录 | 决策可审计 | 决策 × 选择 × 理由 × 替代方案 表（15–25 条，覆盖所有有过分歧的点） |
| 10 附录 | 可执行锚点 | 框架关键文件表；协议原语表（原语 × 用途 × 返回 × 适用）；自定义目录结构树（与仓库实际一致）；术语表（覆盖全部自造名词，30+ 条） |

## 3. 七步写作流程

**步骤一：盘点输入。** 按 §0 表格收齐信息；读现有代码库时，把"实际已存在的约定"记下来，文档必须与代码互证，不能写成科幻小说。

**步骤二：提炼设计原则。** 三条来源，每条产出「名称：机制化一句话」：

- 从痛点反推：痛点"绝不漏患者" → 原则"失败必入待人工集合" → 机制"超时/失败任务强制进入待人工必召回集合，最终结果附未判定清单"；
- 从最坏情况反推：最坏"身份信息泄漏" → 原则"敏感数据隔离" → 机制"不进上下文、不进记忆、不持久化、不随摘要传播"；
- 从历史分歧反推：争论"多组件各筛各的再合并行不行" → 原则"认知并行、数据执行单点" → 机制"单一查询引擎单点执行集合运算，其他组件只输出逐条判断"。

原则命名用 4–8 字短语或对仗短语（如"窄腰宽边""Rule-first, Agent-second"），要能被后文整章引用（"遵循 X 原则"）。控制在 10–16 条，多了等于没有。

**步骤三：建红线分类表。** 列出系统全部组件类型，逐类回答四问：有无 LLM？是否持久？是否自主决策？可否写数据？再配判定准则（"需要自然语言理解 → A/B/C；需要确定性规则 → D/E；需要数据查询 → F/G…"）。这张表放在第 1 章，全文的组件设计都受它管辖。

**步骤四：先写核心章，再回填总览。** 推荐顺序：3（核心架构）→ 7（安全）→ 4（扩展）→ 5（数据）→ 6（集成）→ 2（选型）→ 8（开发模式）→ 1（总览收口）。第 1 章是全文的压缩承诺，核心不稳定时写它必然返工。写作中随手记录 §9 决策记录——每当你写出"选 A 弃 B"，立刻补一行。

**步骤五：画端到端权威时序图。** 用 ```text 画一条从用户入口到落库审计的完整调用链（编号步骤），放在核心章末尾，并声明"本图统一各处措辞"。各节描述若与它矛盾，改各节。

**步骤六：补开发模式与附录。** 分阶段实施必须写"不实现"清单和迁移原则（"先跑通主链再扩展；先关闭危险能力再开放受限能力；先建评估集再迭代"）。目录结构树、术语表放最后——它们是全文稳定后才能写对的部分。

**步骤七：跑 §6 自检清单。** 逐项打勾，不通过回到对应步骤。

## 4. 文风与格式规范

- **原则条目**：`名称：一句话机制化解释`，一句话里要有可检查的动作或边界，不是形容词。
- **表格阈值**：出现 ≥3 个并列对象（技术、组件、Tool、失败场景、事件…）一律用表，不用段落堆叠。
- **表格列型**：直接复用范本列型——"决策 × 选择 × 理由 × 替代方案"、"场景 × 处理策略"、"输入 × 输出 × 权限 × 幂等 × 内部组件"、"阻断项 × 判定内容 × 未完成后果"。
- **数值化**：并发窗口、批次大小、阈值、保留期、置信度门限必须给默认值与建议值（如"默认 3，重负载场景建议 20"）。没有数字的机制无法测试。
- **图**：```text ASCII 时序 / 流程图；图中出现的字段、组件名必须与正文表格一致；一张图只讲一条链路。
- **代码**：核心数据结构给字段级 JSON 示例；扩展组件给元数据 YAML 示例；Tool 给注册函数骨架（Pydantic 输入输出 + 权限声明）；目录给树形结构。
- **引用**：章节间 `§x.y` 交叉引用；需求用编号呼应；口径澄清与边界说明用 blockquote（>）。
- **三处一致**：红线表、设计约束、术语表对同一组件的口径必须逐字一致——范本原文明确要求"分类口径在本表、§3.1 约束与术语表三处保持一致"。
- **版本头**：文档开头四行——版本号、日期、基础框架、核心技术栈摘要。
- **目录**：全文十章完整锚点目录置顶。

## 5. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 口号式原则（"高内聚低耦合"，无机制） | 无法评审、无法测试 | 每条原则配机制与默认值，否则删除 |
| 把规则写进知识文档、把策略硬编码进工具 | 改一条规则要发版 | 四类扩展分离：Skill=怎么做，Policy=何时允许，Rule=确定性判断，Tool=执行 |
| 只有正面设计 | 系统被"临时方案"侵蚀 | 每章配禁止事项；分阶段配"不实现"清单 |
| 意图代替机制（"我们会严格控制权限"） | 落地时各说各话 | 写出审批链的每一步与令牌字段 |
| 组件数量随业务模块线性增长 | Agent/服务泛滥、成本失控 | 按认知职责划分 + 数量克制准则 + 自证表 |
| 自由 SQL 直连、组件持有数据库凭据 | 越权与注入 | 查询模板 + 受控 SQL 白名单 + 凭据集中管理 |
| 二值状态机处理本质不确定的领域（医疗判断只有对/错） | 缺失数据被静默当成功 | 完整状态枚举 + 缺失策略 + 安全默认值 |
| 决策记录没有替代方案列 | 半年后无人记得为什么这么做 | 每条决策必填被否决的方案 |
| 失败路径留白 | 静默降级、静默漏检 | 失败场景表，每类失败有归宿（重试 / 人工集合 / 拒绝），禁止静默 |

## 6. 质量自检清单

交付前逐项打勾：

- [ ] 每条设计原则都能在正文找到对应的机制章节（原则 ↔ 章节映射无孤儿）
- [ ] 红线表、设计约束、术语表三处分类口径一致
- [ ] 每条量化准则配有逐项自证表（✓/✗ + 满足数 + 结论）
- [ ] 每个高风险能力同时具备：权限级别、审批链、审计、失败路径
- [ ] 每个失败场景有处理策略，且明确禁止静默降级
- [ ] 不确定性领域有完整状态枚举 + 缺失策略 + 安全默认值
- [ ] 决策记录覆盖所有"选 A 弃 B"的分歧点，且都有替代方案列
- [ ] 分阶段实施有显式"不实现"清单与迁移原则
- [ ] 合规阻断项有责任归口与"未完成后果"
- [ ] 被取消 / 被合并的组件有记录及理由
- [ ] 术语表覆盖全部自造名词，正文无未定义术语
- [ ] 端到端权威时序图与各节描述无矛盾（声明以此图为准）
- [ ] 目录结构树与仓库实际一致（或标注为目标结构）
- [ ] 全文无 `[待确认]` 遗留

## 7. 裁剪指南

- **不可省**：第 1 章（原则 + 红线）、第 3 章（核心架构）、第 7 章（安全）、第 9 章（决策记录）。
- **可合并**：小型系统可把第 4/5 章合并为"扩展与数据访问"，第 8 章压缩为半页。
- **非 Agent 系统**：把"组件红线表"换成服务/模块分类表（维度改为：是否无状态 / 是否可横向扩展 / 是否触碰敏感数据 / 失败半径），方法论不变。
- **v1.1 迭代**：不重写，先跑 §6 清单找缺口，按缺口补章节；变更记入第 9 章决策表并升版本号。
