## 1. 在系统中的位置

```
合规数据源 / mock 文件
        │
        ▼
  adapters（train.* / flight.*）
        │  Leg[]
        ▼
  规则引擎（枢纽链 → MCT → 打分 → plans）
        │
        ▼
  小程序 / RN App（只展示；购票外链）
```

并行内容流：

```
backend/data/hub-pois.json（TransferPlay）
        │
        ▼
  引擎仅在 buffer ≥ min_buffer_hours 时挂到换乘节点
```

本层职责：

| 做 | 不做 |
|----|------|
| 选型与接入合规火车/航班源 | 违规爬取、模拟登录 |
| 输出定稿 `Leg`；维护 `TransferPlay` | 生成车次号/票价（含模型） |
| 缓存、降级、`source`/`as_of` | 卖票、库存、余票承诺 |
| 密钥走环境变量 / 密钥管理 | 密钥进仓、进小程序包 |

## 2. 适配器契约（稳定面）

目录：`backend/engine/src/adapters/`

| 模块 | 行为 |
|------|------|
| `train.mock.js` | `search({ from_city, to_city, date?, after_at? }) → Leg[]`（仅 train） |
| `flight.mock.js` | 同契约（仅 flight）；默认可扫 `backend/data/mock/legs-*.json` |
| `train.<vendor>.js` / `flight.<vendor>.js` | 后续真源；同契约，密钥仅 env |
| `index.js` | 合并 train+flight，供 pipeline 取腿 |

约定：

1. **首段**可用 `date` 平移日历；**续段**必须用 `after_at: prev.arr_at`，禁止两段都传同一 `date`（overnight MCT 会穿帮）。  
2. 真源与 mock **同一 Schema**，引擎无感切换。  
3. 缓存（落地可先单机）：**默认单机内存 TTL（见 `data-sources.md`）；需要时上 Redis，属部署选择而非产品减配。  
4. 降级：真源 → 未过期缓存 → mock → 可解释空结果（前端三态）。

## 3. 内容资产布局

```
backend/data/
  hub-pois.json              # TransferPlay 独立表（按 hub_city 查）
  mock/
    legs-*.json              # 分段腿原料（徐拉/沪蓉/京汉/成渝…）
    plans-*.json             # 引擎导出的方案（本层不手写三主卡）
  plans-*.json               # 前端/小程序可读副本（由引擎导出同步）
docs/schemas/                # JSON Schema
```

样例 OD（mock 覆盖，非产品承诺全国）：

| OD | 腿文件 | 说明 |
|----|--------|------|
| 徐州→拉萨 | `legs-xuzhou-lhasa.json` | 长线 + 西宁玩法 + 西安空铁 |
| 上海→成都 | `legs-shanghai-chengdu.json` | 经武汉/西安 + 直飞 |

| 成都→重庆 | `legs-chengdu-chongqing.json` | 成渝短途；遂宁/内江为 extraHubs |

头部枢纽维护玩法表（见 `hubs.md`）；其余中转城可有腿、默认不挂玩法，缓冲不够仍不硬推景点。

## 4. 「怎么玩」内容规则

- 表：`TransferPlay`，独立于 `Leg`。  
- 门槛：与产品一致（约同站 ≥2h / 同城 ≥3h / 半日 ≥6h）。  
- 每城目标 3～6 条；西宁为样板。  
- 后续若接地图 POI API：仅官方/合规 SDK，时长与是否赶得回仍需审校。

## 5. 最终设计与落地节奏（数据侧）

1. **阶段 0（工程落地·当前）** — mock 腿 + TransferPlay + adapters；引擎导出 plans；小程序读 JSON/将来 API。  
2. **M1** — `TrainLegProvider` 接一家合规火车源；热门 OD 对照人工答案；密钥与观测就位。  
3. **M2** — `FlightLegProvider`；空铁「最快」走真源+降级。  
4. **M3** — 覆盖扩城、缓存分层、玩法表按枢纽运营更新。

静态 Web 原型：**冻结**（非交付物），仅作历史示意。

## ADR · 数据层：TS 适配器主线 + 多端共享契约

| 项 | 值 |
|----|-----|
| **状态** | Accepted |
| **日期** | 2026-09-23（Asia/Shanghai） |
| **产品** | 懂行（`fasstDog/dongxing`） |
| **关联** | [`ADR-技术栈-TS与多端.md`](./ADR-技术栈-TS与多端.md)；[`ADR-客户端-ReactNative.md`](./ADR-客户端-ReactNative.md)；总架构 §5；本册 §2–§5 |

### 决策

1. **适配器与契约走 TypeScript**  
   - 新 `train.<vendor>` / `flight.<vendor>`、共享 `Leg` / `TransferPlay` 类型只进 TS（目标：`packages/contracts` + `packages/engine` adapters）。  
   - 现有 `backend/engine/src/adapters/*.js`：可 allowJs 挂入 TS 工程；新适配器优先 TS；禁止 Python 取腿/导出脚本。  
   - 仓库内若仍有 Python 数据工具：**冻结只迁不新写**（与引擎册一致）。

2. **多端只共享一份数据契约**  
   - 正式端仅：**微信小程序**（独立，不走 Alita/RN 出小程序）+ **React Native iOS/Android**。  
   - 一律经引擎 API / 同一 Schema 消费 `Leg`→plans；**禁止**各端私造腿表字段或旁路供应商。  
   - Win / macOS / Web / tvOS / Linux / Proton Native / Alita **不进产品范围**（数据层不为这些端单独扩契约）。  
   - `backend/data/mock/legs-*.json`、`backend/data/hub-pois.json` 仍是 DATA-Static；客户端不直接依赖供应商 SDK。

3. **落地节奏（非产品减配）**  
   - 最终设计已锁定；mock adapters 为过渡实现，行为契约不变（`search` / `after_at` / 降级）。  
   - 真源 vendor 用 TS 实现 + Schema 校验；密钥仍仅 env。

### 后果

| 做 | 不做 |
|----|------|
| 数据册与评审按 TS + 多端验收 | 为 App 另起一套 POI/腿 JSON 字段 |
| 新合规源用 TS adapter | 新增 Python 爬取/导出主路径 |
| 与引擎共享类型包演进 | 在静态 Web 原型里接真源 |

### 否决

| 方案 | 原因 |
|------|------|
| 继续用 Python 写新腿导出 | 与全栈 TS 拍板冲突 |
| 小程序 / App 各接各的票源 | 违反窄腰、易编造口径漂移 |
